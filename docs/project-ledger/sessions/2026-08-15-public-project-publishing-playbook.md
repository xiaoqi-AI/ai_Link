# 2026-08-15 公开项目发布经验手册

## 背景

用户要求整理公开项目的发布经验。AI Link 已积累本地 MVP、公开 GitHub 治理、repository-local 发布、provider live 验证、GSC 自动监控、Auth Hub 和跨项目客户端接入等实践，但既有材料分散在维护规则、发布流程和多份会话台账中。

知识库镜像中还保留了一份 2026-07-08 的英文公开仓治理经验稿，尚未作为公开仓正式文档。该稿可以作为经验来源，但知识库镜像不是项目真源，不能未经审查直接覆盖公开仓。

## 本轮目标

- 提供一份中文、系统性、可跨项目复用的公开项目发布手册。
- 区分公开仓、私有仓/密钥系统和本机运行态。
- 明确能力证据等级、人工门禁、发布渠道和发布后运维方式。
- 把 OAuth、调度和外部平台失败的实际踩坑转化为通用判断规则。
- 为项目负责人补充产品、工程、安全、发布和运营五个视角的状态看板。

## 完成内容

- 新增 `docs/00-governance/public-project-publishing-playbook.md`。
- 在 `README.md` 增加手册入口。
- 在 `docs/00-governance/public-github-maintenance.md` 区分“完整方法手册”和“每次更新操作规则”。
- 复用了既有经验，但没有公开 token、OAuth 内容、账号隐私、原始响应、私有路径或内部未脱敏资料。

## 关键经验

1. Public 是仓库可见性，不是发布完成状态。
2. 第一版先证明一条诚实、可运行、低风险的最短路径。
3. 合同和脱敏证据可以公开，真实凭据与账号实现必须隔离。
4. mock、本地 live、CI live 和生产稳定是四个不同证据等级。
5. 人工确认项应作为正式项目决策，包含背景、方案、建议、价值、风险、owner 和证据。
6. OAuth 回调成功、计划任务 Ready、URL 返回 200 都只证明局部事实，不能替代端到端验收。
7. 外部平台暂态、AI Link 自动化故障和消费项目故障必须分别归责。
8. GitHub 是公开项目真源，知识库用于长期上下文与交接。

## 边界

- 本轮只更新公开文档和项目台账。
- 不修改 CLI、provider、connector、Auth Hub、GSC 自动化或发布配置。
- 不创建 tag、不发布 npm、不部署服务、不调用真实外部平台。
- 公开发布动作仍遵循 `docs/00-governance/release-process.md` 的独立人工门禁。
