# 公开项目发布与持续维护手册

## 1. 这份手册解决什么问题

把仓库改成 Public 只是公开项目的一个动作，不等于项目已经具备公开发布条件。

一个可持续的公开项目至少要同时做到：

- 陌生用户能判断项目是什么、当前能做什么、如何开始。
- 维护者能证明代码、包、文档和发布声明与实际状态一致。
- 真实账号、密钥、登录态、原始响应和内部决策不会进入公开历史。
- 外部系统接入时有稳定合同，不需要复制项目内部实现。
- 发布后的故障能区分为项目问题、外部平台问题和自动化问题。

本文汇总 AI Link 从本地 MVP、公开仓治理、provider live 验证、GSC 自动监控和跨项目消费验收中形成的可复用经验。具体命令仍以本仓库其他治理文档为准。

## 2. 最重要的经验

### 2.1 先公开一个诚实的最小能力

第一版应先回答三个问题：

1. 用户为什么需要它。
2. 用户能在五分钟内完成哪条无密钥或低风险路径。
3. 哪些能力尚未完成、尚未实测或仍需人工批准。

不要用路线图代替可运行结果，也不要把脚手架、mock 或本地实测描述成生产能力。

### 2.2 把公开、私有和运行态分成三层

| 层级 | 适合保存 | 禁止或应避免保存 |
| --- | --- | --- |
| 公开仓 | 源码、稳定合同、mock、示例配置、脱敏文档、公开安全证据 | token、Cookie、登录态、原始响应、私密截图、个人路径、内部账号信息 |
| 私有仓或密钥系统 | 未公开规划、运维说明、供应商评估、密钥引用、受控适配器 | 无限制复制公开仓、长期明文密钥、缺少 owner 的共享凭据 |
| 本机运行态 | 临时授权文件、浏览器 Profile、原始调试材料、生成报告 | Git 跟踪、知识库同步、公开 artifact |

公开仓应能独立解释其公开能力；不能依赖读者访问私有仓后才理解基本用法。

### 2.3 公开合同，隔离真实凭据和账号实现

对 provider、connector 或远程平台集成，优先公开：

- 输入输出合同。
- 配置字段和环境变量名。
- mock / dry-run 行为。
- policy gate 和错误码。
- 脱敏验收摘要。

真实凭据、浏览器登录态和账号特有逻辑留在私有适配器、密钥系统或本机运行态。这样既能让公开项目可复用，也不会迫使下游项目复制敏感实现。

### 2.4 用证据等级约束发布声明

能力声明应标明证据等级：

| 等级 | 已证明 | 不能据此声称 |
| --- | --- | --- |
| 合同 / mock 通过 | 接口形状、路由和基本状态机可工作 | 外部平台可用 |
| 本地 live 通过 | 当前维护者机器和当前账号完成一次真实调用 | CI、其他账号或生产环境可用 |
| CI live 通过 | 受控 CI 环境能完成真实调用并生成脱敏证据 | 长期稳定或生产 SLA |
| 生产观测稳定 | 调度、刷新、失败分类和恢复流程经过持续验证 | 永久免维护 |

发布说明只写已经有证据支持的级别。AI Link 的实践证明，“本地真实调用通过”和“GitHub Actions 中已配置并持续通过”是两个不同结论。

### 2.5 把人工确认设计成正式决策

账号权限、费用、域名、生产密钥、发布、真实调用和外部平台写操作都不是临时阻塞，而是项目决策。

每个决策项至少应写明：

- 项目背景和当前进度。
- 本次需要决定的具体事项。
- 可选方案及影响。
- 推荐方案、价值和风险。
- 谁负责执行。
- 什么证据代表完成。
- 如果暂缓，项目还能推进到哪里。

这样可以优先处理真正需要负责人的事项，同时让本地开发、mock、文档和安全验证继续进行。

### 2.6 文档是公开产品的一部分

最小文档面建议包含：

- `README`：定位、状态、快速入口、限制。
- Quickstart：无密钥或最小权限的最短成功路径。
- User guide：完整使用方式和常见失败。
- Architecture：稳定合同、边界和数据流。
- Contributing：贡献流程、测试要求和行为预期。
- Security：私密报告渠道和不应公开的信息。
- Changelog / release notes：实际发布内容、兼容性和已知限制。

功能改变时，用户入口应与代码在同一个 PR 中更新。文档滞后本身就是公开接口缺陷。

### 2.7 发布渠道必须显式选择

“代码已在 GitHub”不等于“已发布软件包”。常见渠道包括：

- `repository-local`：从仓库安装或直接运行，适合早期 MVP。
- GitHub Release：有 tag、版本说明和可追溯快照。
- npm / PyPI 等包仓：需要包内容、版本、owner 和回滚策略。
- 托管服务：还需要部署、域名、访问控制、数据和运维责任。

渠道选择要记录为决策。没有发布 owner、回滚方式或长期维护承诺时，优先保持 `repository-local`。

### 2.8 授权不是一次性设置，而是运行能力

OAuth、CLI 登录和 refresh token 会受到应用发布状态、账号策略、代理、计划任务环境和平台规则影响。可靠的自动化需要分别验证：

- 授权文件是否存在。
- 当前只读调用是否成功。
- 刷新是否成功。
- 计划任务是否真的运行成功，而不只是状态为 Ready。
- 失败属于授权、权限、网络、代理、配额、平台暂态还是业务对象。

浏览器显示“授权成功”只证明回调已到达；必须以 token 交换和后续只读 API 调用成功作为完整证据。

### 2.9 业务故障与基础设施故障必须分开

自动报告至少应区分：

- 业务项目故障：站点不可达、robots 阻止、canonical 错误、`noindex`、合同不兼容。
- 外部平台状态：Google 尚未索引、第三方 API 暂时不可用、平台配额等待。
- AI Link 自动化故障：OAuth 失效、代理缺失、任务漏跑、报告过期、适配器异常。

只有第一类通常需要修改消费项目。第二类以观察或人工平台动作处理；第三类应修复 AI Link 的授权、调度或适配器，不能误改业务项目。

### 2.10 GitHub 是公开项目真源，知识库是上下文镜像

多电脑和多 Agent 协作时：

- 远端受保护默认分支代表公开项目状态。
- PR、检查和合并记录代表变更证据。
- 知识库镜像保存决策背景、踩坑和跨项目交接。
- 会话历史只作辅助，不能替代仓库文档。

镜像中出现但公开仓没有的经验，应先审查、脱敏和改写，再决定是否提升为公开文档；不要直接反向覆盖公开真源。

## 3. 推荐发布流程

### 阶段 A：确定是否应该公开

在创建公开仓之前确认：

- 一句话定位和目标用户。
- 当前能力、非目标和成熟度。
- 许可证和第三方资产许可。
- 是否含有客户数据、账号数据、内部路径或不可公开依赖。
- 哪些集成只能公开合同，不能公开真实配置。
- 谁是维护者、安全联系人和发布 owner。

以下情况建议暂缓公开：核心价值只能依赖私密数据解释；历史中已有未清理密钥；第三方代码或素材许可不明确；没有人承担安全响应和版本维护。

### 阶段 B：建立公开基线

1. 建立 `README`、Quickstart、User guide、License、Contributing 和 Security。
2. 提供无密钥 smoke path、mock 或 dry-run。
3. 配置 `.gitignore`、包白名单和敏感扫描。
4. 为 `main` 配置禁止强推/删除、PR 和必要状态检查。
5. 用示例值替代真实账号、域名、路径和 secret。
6. 检查 Git 历史，而不只检查工作区当前文件。
7. 建立公开 issue / PR 模板，让反馈可操作。

### 阶段 C：首发验收

首发至少证明：

- 全新环境能按 Quickstart 成功。
- 构建、类型检查和测试通过。
- 包内容与预期一致，安装后的入口能运行。
- 示例配置可验证。
- 敏感扫描和治理检查通过。
- 发布说明准确描述能力等级和限制。
- 所有人工门禁都有 owner、状态和证据。
- 本地分支与远端 PR 状态一致。

### 阶段 D：发布动作

发布动作应按风险从低到高分开执行：

1. 合并受检查保护的 PR。
2. 确认默认分支和文档页面正确。
3. 创建签名或注释 tag。
4. 创建 GitHub Release。
5. 如已批准，再发布包或部署服务。

Tag、包发布、生产部署和真实外部写操作应分别保留人工门禁，避免一次“发布”授权被无限扩大。

### 阶段 E：发布后维护

每次重要更新都要确认：

- 用户入口仍然准确。
- 兼容性变化已有迁移说明。
- 自动化报告新鲜，且失败原因可分类。
- issue、安全反馈和依赖更新有负责人。
- 已废弃能力有时间表，不突然删除。
- 公开声明仍与最新证据等级一致。

## 4. 项目负责人应掌握的看板

公开项目看板不应只记录“提交了哪些代码”，而应至少有以下五类状态：

| 视角 | 关键问题 | 推荐证据 |
| --- | --- | --- |
| 产品 | 本阶段解决什么问题，下一阶段为何值得做 | 需求边界、路线图、验收结果 |
| 工程 | 当前能力是否可安装、可运行、可回归 | CI、测试、包 smoke、兼容性记录 |
| 安全 | 哪些数据和动作受保护 | 扫描结果、公开/私有边界、人工门禁 |
| 发布 | 当前渠道、版本和声明是否准确 | decision record、tag、release notes |
| 运营 | 发布后是否稳定，问题属于谁 | 脱敏监控、错误码、owner、恢复记录 |

建议只在状态变化、出现新风险或需要决策时通知负责人；普通成功运行不重复消耗注意力和 token。

## 5. 跨项目提供能力的方式

公开中间层不应接管消费项目主流程。推荐分工：

- AI Link 维护 provider / connector 合同、策略、授权边界、统一客户端和脱敏审计。
- 消费项目维护自己的业务编排、内容规则、领域校验和最终修复。
- 真实账号由明确 owner 管理，通过本机、CI Environment 或密钥系统按最小权限注入。
- 消费项目只在命中特定触发条件时读取完整接入手册，不在普通开发中反复检查外部能力。

接入验收应先走 mock / dry-run，再走本地只读 live，最后才考虑 CI、远程部署或写操作。

## 6. 常见失败及其正确解释

| 现象 | 不能直接得出的结论 | 正确处理 |
| --- | --- | --- |
| OAuth 回调页成功 | refresh token 已保存且可长期使用 | 验证交换结果和一次只读 API 调用 |
| Windows 任务显示 Ready | 最近一次任务成功 | 同时检查最近结果码、时间、下次运行和漏跑次数 |
| 公开 URL 全部 200 | Google 已索引 | 分开报告公开技术状态和搜索引擎状态 |
| 单次第三方 API 失败 | 业务站点有问题 | 先按授权、权限、网络、代理、配额和平台暂态分类 |
| 本地 live 通过 | CI live 已配置 | 分别记录本地与 CI 证据等级 |
| 包 dry-run 内容正确 | 安装后 CLI 可运行 | 再做临时空项目安装 smoke |
| 仓库当前没有 secret | Git 历史没有 secret | 扫描完整历史并轮换曾暴露的凭据 |

## 7. 最小发布检查清单

### 产品与文档

- [ ] 一句话定位、目标用户和当前成熟度清晰。
- [ ] Quickstart 在全新环境可完成。
- [ ] 非目标、限制和未实测能力写明。
- [ ] 用户指南、贡献指南和安全反馈入口可达。

### 工程与质量

- [ ] 构建、类型检查、测试通过。
- [ ] 包内容和安装 smoke 通过。
- [ ] 示例配置不依赖维护者本机路径或账号。
- [ ] 破坏性变更有迁移说明。

### 安全与治理

- [ ] 当前文件和 Git 历史均通过敏感扫描。
- [ ] 真实 secret、登录态、截图和原始响应不在公开仓。
- [ ] `main` 受保护，必要检查已配置。
- [ ] 外部费用、账号、发布和写操作都有人工门禁。

### 发布与运维

- [ ] 发布渠道、版本、owner 和回滚方式已决定。
- [ ] Release notes 与实际证据等级一致。
- [ ] 监控输出脱敏、可分类、可判断是否需要业务修复。
- [ ] 发布后反馈、安全响应和弃用流程有负责人。

## 9. 完成标准

一个公开项目可以认为“已发布并可维护”，需要同时满足：

- 新用户无需维护者口头解释即可完成最短成功路径。
- 公开声明与证据等级一致。
- 敏感数据不进入公开仓、包、日志或知识库镜像。
- 主分支和发布动作可追溯、可回滚。
- 外部能力失败时能判断由哪个项目或平台处理。
- 维护者知道下一项决策、风险和 owner，而不是只看到提交数量。
